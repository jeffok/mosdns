# Unified .222 candidate and deployment state — 2026-11-14

The source builds one image containing mosdns and the BGP agent. The legacy RouterOS REST address-list plugin and synchronizer were removed. Global/AI winning responses are tagged through fallback and confirmed with the local agent before release; direct/CN/hosts responses retain distinct provenance. BGP mode disables the untagged mosdns cache, enforces IPv4-only mode and disables agent direct prewarming. Agent confirmation uses a loopback-only client, snapshots reject stale/reordered generations, confirmed routes are fsynced before DNS answer, and restart replays persisted routes. Route GC in agent is generation-aware, but this does not implement RouterOS blackhole lifecycle.

On szhome the old .222 container was replaced with local image `jeffok/mosdns:bgp-unified-20261114.2`, using the same veth, rules and data mounts. It runs **DNS-only mode**: BGP_EMBEDDED and ENABLE_ROS_BGP remain unset, because household routing and guard GC are not ready. `start-on-boot=yes`, `restart-policy=on-failure`. Direct DNS queries for baidu.com and github.com from ROS to .222 succeeded. The plain-mode mosdns child was killed and its PID changed from 273 to 322; both queries succeeded afterward. This verifies child supervision, not RouterOS automatic restart of the entire container. ROS household DNS remains `119.29.29.29`; do not describe .222 as the household resolver. Only one container remains. Prior .223/.224 test containers, interfaces, routing objects and test directory were removed. No BGP session is configured.

ROS www has been disabled as authorized. Old REST-only environment keys and `mosdns` user/group were removed. RouterOS retained 13 stale `mosdns` REST entries in `/user active` and each `remove` failed; this is not claimed cleaned, and the account and www service no longer exist/enabled. No credential is included in this document. A backup archive for the old image is available as `mosdns-old-rollback.tar`; its mosdns binary matched the prior running container's SHA-256. Previous rules/data backups are available in the mounted data directory and in local `.cache/bgp-agent/production-replacement`.

Local checks against the candidate: `go test -race ./...` and `go vet ./...` in bgp-agent; actual DNS fallback/confirm/IPv6 integration `tests/bgp-integration.sh`; original core tests 8/8; child-process supervisor tests; and `tests/bgp-combined-real.sh` with the actual agent and mosdns showing domestic DNS success and global SERVFAIL when there is no BGP peer. A separate earlier .223 experiment verified that confirmed state survived forced container termination and that a test-table blackhole became active on BGP loss. Those experiments do not verify the final .222 BGP dataplane or real RouterOS crash/power loss.

## Same-container .222 isolated end-to-end check

The only .222 container was temporarily switched to combined BGP mode with DNS bound to loopback and a disposable test routing table restricted to its own source. Household DNS remained 119.29.29.29. In this test baidu.com returned NOERROR (one observed TTL was 315 seconds, revealing that direct/CN TTL is not yet capped at 300). github.com returned NOERROR after 3.23 s and HTTPS 200; a BGP /32 via ovpn-szof and a matching inactive static blackhole were observed. After disabling the isolated BGP connection, the blackhole became active, direct HTTPS to the saved IP timed out, and DNS returned SERVFAIL with no answers. After re-enabling the peer, github.com returned NOERROR and HTTPS 200. This verifies a representative same-container path, not household forwarding, long-lived guard GC or arbitrary external clients.

The temporary BGP connection, isolated table, local scheduler, test blackholes, connection marks, config and BGP environment settings were removed afterward; .222 was restarted in DNS-only mode with its prior 0.0.0.0:53 listen, and a domestic query succeeded. Only one container remains; household DNS is unchanged. The production candidate cannot be switched to household BGP based on this test alone. DNS direct/CN TTL cap remains to be fixed, and ROS query-server-timeout=2s is below this test's initial 3.23s combined response time.
