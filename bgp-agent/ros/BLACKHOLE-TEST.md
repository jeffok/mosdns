# Experimental BGP fallback guards

`ack-blackhole-test.rsc` is a **test-only draft**, not production deployment. It targets RouterOS 7.24.6, `rt-bgp-test`, .223/.254 and the existing OVPN gateway. It adds persistent static /32 blackhole routes at distance 240, lower priority than the BGP path at distance 20 and more specific than the direct default. It is intended to prevent previously answered test addresses from falling through to the test table's direct default when their BGP route disappears.

For each desired BGP /32, it attempts to create a route owned by exact comment `BGP-TEST-BH:<prefix>` before acknowledging that prefix. It re-reads the namespace and checks the route is enabled, static, blackhole, in the test table, at distance 240, with matching destination and comment. It then rechecks BGP is active on OVPN at distance 20 and rejects an active same-prefix competitor. Duplicate namespace comments fail the entire cycle; ambiguous objects are neither modified nor adopted. The namespace has a global cap of 512 routes. When full, already guarded destinations can be acknowledged but additional ones cannot. Desired epoch and single-use snapshot ID are preserved; checks which exceed their time budgets do not post ACK.

**Readback only verifies the running configuration. It does not establish that an unexpected power loss cannot lose a recent configuration write.** The script also cannot guarantee atomicity between readback, ACK and packet forwarding, or protect clients whose traffic does not use `rt-bgp-test`. It requires routing-table existence and source-specific routing rules to survive reboot; test these separately. The guard fallback intentionally drops traffic and cannot keep an existing long connection alive when BGP/OVPN fails.

## Before any live use

1. Review the script as a separate named object. Disable the original `bgp-test-ack` scheduler before enabling a new scheduler: the old script would otherwise acknowledge unguarded routes. Do not modify household DNS, main table or unrelated routing rules.
2. Ensure the RouterOS script and its scheduler have narrowly authorized `read,write,test` policies. Write permission is new and permits route changes; isolate access. Verify named-job overlap guard prevents concurrent runs. The pre-existing scheduler lacks write policy.
3. Use `/import ... verbose=yes dry-run` on the actual ROS version. In a disposable test table verify `print detail as-value` includes `.id`, `dst-address`, `comment`, `distance`, and that `where static and blackhole and !disabled` matches an inactive backup guard. Check prefixes, array operations, invalid/duplicate owners, route additions and deletion semantics. The operator observed that `!disabled` matches the inactive backup whereas `disabled=no` did not; other fields and syntax still need end-to-end validation.
4. Capture DNS and packet behavior from .223: fresh response only after both the BGP route and guard exist; first SYN via OVPN; disable BGP and confirm the guard becomes active and traffic is dropped, then restore BGP. Test missing, disabled, wrong-table, wrong-distance, wrong-prefix, duplicate and unrelated routes, ECMP conflicts, capacity and overlapping jobs. Test ACK timeout, stale snapshot and POST failure. An active-route observation alone is not packet-delivery evidence.
5. Exercise orderly RouterOS restart, then a controlled power interruption where operationally safe. Verify guards and routing marks are available before cached client traffic, and disclose whether the very last writes survived. Readback alone is not power-loss verification. Measure route-create latency and CPU/flash-write load at realistic scale; 512 route adds can exceed ACK budget or stress storage. Do not infer production capacity from 512.

## Cleanup and limits

There is deliberately **no automatic cleanup**. Removing a guard while clients retain an old DNS answer or an existing connection can restore direct fallback; even DNS TTL plus five minutes cannot establish that all long connections have ended. The cap will eventually exhaust as destinations change, making this unsuitable as a long-term solution without a separately designed, tested lifecycle mechanism and a recovery path. The namespace must not be shared with other services.

For an explicitly isolated rollback, first stop test traffic and the new scheduler, allow or deliberately terminate relevant cached answers/connections, then inspect `/ip route print detail where comment~"^BGP-TEST-BH:"` and remove only exact inspected owned routes. Do not bulk-delete routes by prefix alone, modify main table routes, or treat the namespace as proof of ownership without checking destination, table, blackhole flag and comment. Restore the original scheduler only after its consequences are understood. A mismatch in a foreign table or duplicate comment must be resolved manually.
