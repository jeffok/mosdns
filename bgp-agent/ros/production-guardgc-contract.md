# Disabled production guard-GC wire draft

Status: **design draft; not integrated or verified**. `production-guardgc-draft.rsc` creates no scheduler and has both `enabled=false` and `mutationEnabled=false`. The actual agent in this repository does not expose `/guardgc/next` or `/guardgc/ack`; its existing `/desired` and `/ack` endpoints must not be repurposed for destructive GC. Do not enable the script on production or claim working automatic GC. The existing durability coordinator is not a RouterOS integration.

## Scope and prerequisites

The draft is constrained to agent `192.168.88.222:9080`, ROS source `192.168.88.254`, IPv4 /32 and `main`; guard ownership is exact `BGP-PROD-BH:<generation>:<canonical-prefix>`, enabled static blackhole distance 240, with BGP distance 20. This namespace must match the eventual production guard creator; it is deliberately distinct from test-table guards. The scheduler must be a **single serialized ROS writer for both normal guard ACK and GC operations**: a separate GC scheduler alongside a normal ACK scheduler can race and is forbidden. A named-job guard alone does not coordinate different script names or manual scripts. No source in this draft enforces this global single-writer contract.

Authoritative persisted agent state must freeze each prefix during each pending op, survive agent crash, block new DNS answers/re-adds until reconciliation, validate BGP/guard state and TTL exposure on its own, enforce last-issued DNS TTL plus send bound, and wait for two empty conntrack snapshots separated by a verified conservative quiet interval. Every pending operation has an immutable ID and generation across restarts. Replayed or mismatched ACKs do not advance state. If controller recovery, ROS job overlap, operator action or flash persistence is unknown, leave barriers and guards in place and do not answer new DNS for affected prefixes. IP source filtering is not authentication; restrict router and LAN access to the management path.

A separate forward and output passthrough anchor must be provisioned and checked manually as `BGP-PROD-GC-ANCHOR:forward` and `BGP-PROD-GC-ANCHOR:output`, positioned before **all** accept, FastTrack or jump rules for the respective chain. The draft rejects ambiguous anchors and such early rules, but cannot prove BGP peer origin from gateway/active flags: no other peer may originate these main-table prefixes unless origin verification is added. It also cannot prove correctness of bridge/hardware bypass, RAW NOTRACK, external routing or future manual changes. Disable FastTrack/hardware offload and ensure all relevant IPv4 traffic goes through conntrack and these chains; establish bounds for in-flight packets and conntrack visibility. Separate LAN→LAN, router-originated, NAT and OVPN flows require review. Domestic and overseas names may share an IP, so a temporary IP-wide barrier can block domestic services.

## Proposed wire schema

`GET /guardgc/next` (accepted from the ROS management source only) returns either:

```json
{"version":1,"action":"idle"}
```

or exactly one durable pending operation:

```json
{"version":1,"epoch":"0123456789abcdef01234567","operation_id":"111111111111111111111111","generation":"222222222222222222222222","prefix":"20.205.243.166/32","action":"observe_conntrack"}
```

`epoch`, `operation_id`, and `generation` are 24-character lowercase hexadecimal strings; prefix is canonical IPv4 /32. Allowed ROS actions are `install_barrier`, `observe_conntrack`, `observe_withdrawn`, `remove_guard`, and `remove_barrier`. The agent itself withdraws BGP; ROS never executes that mutation. The read-only `observe_withdrawn` request additionally carries a 24-hex `parent_operation_id` of the agent’s pending `withdraw_bgp` operation and has its own probe operation ID. The dispatcher must bind both IDs, epoch, generation, prefix and observation to the still-pending parent before constructing its withdrawal proof. An operation is never replaced, canceled or assigned to another generation while its external effects or a previous ROS job may still execute. On crash, reconcile the same durable pending ID before permitting a new operation. This means DNS for that prefix can be unavailable while uncertain; that is intentional fail-closed behavior.

`POST /guardgc/ack` includes `version`, all identity fields, `action`, `parent_operation_id` (empty except for `observe_withdrawn`), `result:"ok"`, and an `observation` object with `exact_owner`, `barrier_verified`, `snapshot_complete`, `connections`, `guard_present`, `bgp_active`, `guard_absent`, `bgp_absent`, `barrier_absent`, `rechecked`. `barrier_verified` describes the verified barrier *before* a remove operation. `snapshot_complete` and nonnegative `connections` are present as evidence only after a full successful scan; no scan uses `false` and `-1`. The dispatcher maps `barrier_verified` to BarrierPresent except on a completed remove_barrier, `snapshot_complete && connections == 0` to NoConnections, `guard_present` to GuardPresent, `bgp_active` to BGPActive, `guard_absent` to GuardAbsent, `bgp_absent` to BGPGone, `barrier_absent` to BarrierAbsent and `rechecked` to Rechecked; `exact_owner` is required on every successful transition. Guard/BGP absence claims must be independently checked per action. The coordinator must check exact epoch/operation/generation/prefix/action, live frozen state, expected action-specific evidence, and its own monotonic quiet/TTL deadlines. A nonzero connection count is an observation, not permission to withdraw. The draft sends no ACK on any error; the coordinator must not interpret silence as success.

## Draft actions and safety boundaries

- `install_barrier`: checks anchors and inserts an exact destination drop per chain for each of `new`, `invalid` and `untracked`, total six rules; verifies enabled status, action, chain, connection state, dst-address and position before anchors. At most 192 namespaced rules (32 simultaneous prefixes) are allowed. Retains existing tracked connections. Partial additions are reconciled idempotently. The two writes switches must be manually enabled only in a disposable isolated test.
- `observe_conntrack`: requires exact barriers, same-generation guard, an active distance-20 OVPN BGP route with no active competitor, and scans one RouterOS connection snapshot. It inspects source/destination and reply source/destination, stripping the IPv4 port before exact host comparison. Missing or empty tuple fields are treated as unknown and result in no ACK. The coordinator performs repeated observations and quiet-time checks; one empty scan is not proof all packets have drained.
- `observe_withdrawn`: a **read-only** child probe attached to a still-pending agent `withdraw_bgp` operation; requires exact barriers and same-generation guard, no BGP path, and a complete conntrack observation. The dispatcher may map its proof to the parent withdrawal only when all identity fields and parent are still current, and connections are zero. There is no agent dispatcher or HTTP bridge yet.
- `remove_guard`: requires the verified barriers, a fresh zero-connection snapshot, absence of any main-table BGP route for the target, and exactly one correctly owned enabled static blackhole route. It removes only that exact object and verifies namespace absence. An already-absent guard is deliberately blocked: without a durable ROS-side deletion receipt, an absent object does not prove this exact operation removed the expected owner. Manual reconciliation or a separately verified durable receipt protocol is required after a lost ACK. It never removes the firewall barrier.
- `remove_barrier`: first reinstalls/rechecks all six exact barriers (handles a partially completed previous attempt), takes a fresh zero-connection snapshot, and requires both BGP and owned guard absence; it removes only the exact six rules and checks their labels are absent, then rechecks no connections, owned guard or BGP route. This sequential operation relies on the controlled-client/TTL and frozen-prefix assumptions; it is not atomic against physical packets or external operators. A crash mid-removal requires reconciliation. It allows future bypass traffic to use the electric default after completion.

Any route or firewall configuration readback reflects running state and does **not** establish fsync or sudden-power-loss durability. A long-lived tracked connection can keep a barrier indefinitely; the cap then makes new admissions fail closed. If all states eventually need to be bounded while also guaranteeing protection for devices using hardcoded IP/DoH, stale TTLs, unknown sources or IPv6, this architecture cannot satisfy both requirements; consider a fixed fail-closed destination range with a transparent proxy instead.

## Required verification before integration

1. Unit/model tests: durable prefix generation and op ID, exactly-once admission, max-size multi-IP reservation, pre-response persisted TTL watermark, in-flight write pin, GC vs re-add, old ACK/replay/reorder, all-or-none capacity failure, controller crash at each external effect, persistence write errors, clock jumps/restart TTL grace, long conntrack retention. See `../guardgc-model/` for a model, not production evidence.
2. Disposable ROS sandbox: `/import ... verbose=yes dry-run`; verify `:toip`, ip-prefix/string conversion, filter `get` field types, rule ordering, anchor matching, six-rule ownership, partial-add/remove crash replay, duplicate/malformed owners, zero/full conntrack tuples (including NAT, ICMP and IPv6), exact host matching, BGP and guard presence, ACK JSON and epoch handling. The draft has **not** been parsed or run on ROS by its author.
3. Packet path: concurrent new/existing TCP and UDP flows, NAT original/reply tuples, first-packet OVPN egress, blocked new flows while established flows remain, re-add while each operation is pending, IPv4 fragments and every permitted client ingress. Observe false-negative/unknown conntrack behavior, ROS control-plane failures and scheduler overlap. Measure CPU, worst-case rule write/scan time and flash writes with realistic concurrent load.
4. Crash test actual agent, ROS script, BGP session and RouterOS separately after each intent/effect/ACK boundary, including controlled power-loss only where safe. Confirm guard and barrier persistence and journal fsync on real storage. Uncertain persistence or inability to bound in-flight packets means no automatic barrier/guard removal.
5. Only after the full mosdns domestic/overseas selected-answer integration, agent coordinator, firewall contract and tests pass, consider a production migration with explicit rollback. This document, script and model do not authorize or establish that migration.
