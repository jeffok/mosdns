# Guard GC: proposed controlled-client protocol

This is a design and executable **model**, not RouterOS or agent production code. Run `python3 -m unittest discover -s bgp-agent/guardgc-model -v`. The model assumes external operations are idempotent and durable; passing it does not verify actual GoBGP, storage, ROS firewall ordering, connection tracking, or power-loss behavior. This protocol is *not* an unconditional no-leak guarantee.

## Explicit operating assumptions

- Only controlled IPv4 clients on inventoried LAN paths use the protected service; no hard-coded target IP, direct external DNS, DoH, IPv6, hostile or TTL-ignoring cache is claimed protected. All cooperating caches honor the returned TTL, at most 300 seconds; DNS packet transit and client scheduling have a measured conservative bound `send_margin`. Guard removal is conditional on these assumptions and a measured router dataplane quiescence bound.
- Every relevant forwarded/output flow passes ROS firewall and conntrack. Disable FastTrack and hardware offload; no RAW NOTRACK or bridged bypass; include router-originated traffic and all relevant interfaces, fragmented traffic, NAT and reply tuples. Confirm these properties at deployment and after any rule change. Block or reject untracked new traffic during drain. Exact ordering is verified by counters/packets, not guessed from config alone.
- Different names and clients can share an IP; routing in `main` is per IP and may force domestic traffic through OVPN. A drain barrier may temporarily block new legitimate traffic to that shared IP. This is an acknowledged service tradeoff, not name-level isolation. RouterOS readback is not proof of flash persistence; last-write power-loss survival must be verified and treated as a precondition, or the protocol remains blocked.

## Persisted record and serialization

For every /32, atomically journal `{prefix, generation, phase, answer_expiry, last_commit, pending_op, bgp_uuid, guard_owner, barrier_owner}` before the corresponding externally visible action. Generation is unique across restart/re-add; op ID is unique and persisted. Exact owned static routes/rules include prefix, generation and operation identity; other objects are never adopted or removed. Use append+fsync or temp+fsync+atomic rename+directory fsync, with explicit storage-failure fail closed and tests on the actual mounted filesystem. Do not clear a dirty flag before persistence success. Preserve all earlier records until the whole transaction is durable. This proposal does not claim the current durability implementation has these properties.

A single agent coordinator owns `prefix -> state` and serializes publication, answer reservation, retirement and re-addition under a per-prefix lock. Multi-IP DNS responses lock prefixes in sorted order, reserve all slots and pins atomically, confirm all guards/routes, and persist the full response horizon before sending any positive response. Roll back only resources created by the failed transaction; never evict live prefixes. An in-flight answer pins each prefix. Its durable expiration is at least `issue_time + TTL + send_margin`; enforce a bounded send deadline and do not emit a reply if exceeded. Retirement first transitions ACTIVE→DRAINING under that same lock, prevents additional pins/positive DNS answers and waits for pre-existing answer pins to complete. A query received while cleanup is pending returns SERVFAIL or waits within a bounded request deadline; it MUST NOT silently restart a new generation before the old operation is reconciled.

Use monotonic deadlines during one process lifetime. Persisted wall clock alone is unsafe across reboot or NTP steps; on restart conservatively wait a fresh `max_TTL + send_margin + clock_uncertainty` from recovered readiness before considering any retirement, and block if local time or previous durable journal cannot be trusted. Keep route state and DNS exposure records across crash.

## Existing interfaces and single ROS writer

Extend `/desired` compatibly with immutable `{prefix,generation,action,operation_id}` entries and retain current epoch and one-use snapshot_id. Extend `/ack` to report the same exact operation identity and read-back outcome. Agent rejects unknown, stale, replayed, superseded or wrong-generation acknowledgements. `/desired` is restricted to ROS peer; `/ack` already validates the source IP, but IP identity is not authentication. Run one named ROS scheduler only, with job-overlap guard; the old ACK scheduler must be disabled. ROS does not accept independent route mutations from the agent or a second scheduler. Router-side commands must be idempotent and verify exact object ID, owner, route/table/type/distance and firewall order; refuse collisions and partial readback.

A durable agent intent is written before ROS receives an operation. After crash/restart a pending operation remains pending and answer admission for that prefix stays shut until the *same* operation is reconciled against ROS readback, after any old named job has completed. ROS keeps barriers in place on error. Agent never starts a new generation while a prior delete or barrier removal can still run; stale ACK/token cannot authorize new-generation effects. Because RouterOS does not provide a single atomic compare-and-delete transaction over its configuration, this serialized-owner assumption and fail-closed reconciliation are essential. If a stale job, competing operator, failed journal or unknown route ownership cannot be excluded, leave the barrier/guard in place and alert rather than deleting.

## Lifecycle

1. NEW: reserve capacity for the entire multi-IP answer. Create/verify BGP /32 and static blackhole guard (distance higher than BGP but more specific than direct default), then observe actual active BGP and guard ownership. ROS confirms only current snapshot/gen. Persist publication and answer horizon before the DNS write. On route/guard failure return SERVFAIL, and retain any uncertain guard for reconciliation.
2. ACTIVE: preserve guard and BGP while any domain reference or issued DNS answer is live; prewarm refresh extends relevant references. Snapshot ACK verifies bounded-age FIB observations, not remote tunnel health. Do not treat BGP session established or active route as proof of end-to-end OVPN connectivity.
3. DRAINING: after retention, references, durable answer horizon, and pins permit, reject new DNS admission for that prefix. Once last exposure + send_margin + configured safety window has passed, ROS single writer installs *persistent*, exact-prefix new-connection barriers before existing forward accepts/FastTrack, plus an output-chain barrier if router-originated traffic falls within scope. Verify table, matcher, position, enabled state and both required chains before ACK. Keep current BGP route and guard while existing connections drain. A new request waits or SERVFAILs; do not cancel an in-flight deletion by changing generation underneath ROS.
4. BARRIER: after a verified barrier and measured dataplane quiescence interval, inspect all relevant IPv4 conntrack entries by original destination and NAT/reply tuple; take repeated consistent empty observations separated by the measured bound. If any flow is present, routing state is uncertain, or conntrack visibility cannot be proven, retain both route and barrier indefinitely. Active long connections can prevent reclamation indefinitely. Once zero under the stated assumptions, agent withdraws BGP with persisted operation intent, waits for its actual absence, and retains the guard and barrier.
5. WITHDRAWN: after no active/eligible BGP path and no connections, ROS removes only the exact owned guard. A wrong owner, duplicate, missing readback or ambiguous state is a hard stop; keep barrier. Verify guard absence. Persist/ack before advancing.
6. GUARD_REMOVED: a separate operation may remove the barrier only after the above TTL, conntrack, quiet-period and controlled-client assumptions remain true. Recheck them immediately before removal. While this op is pending, agent blocks new answers and generations; only after exact barrier absence readback and durable ACK does it enter RETIRED and release the reserved slot. This step deliberately permits future raw packets to fall back to main/electric direct and thus does **not** protect bypass clients or stale caches. Any failed operation leaves DNS closed and persistent barrier in place until reconciled.
7. RE-ADD: only after RETIRED is durable may a new query allocate a fresh never-reused generation. Recreate/confirm guard+BGP and persist a new exposure horizon before DNS response. Old operation IDs and old snapshots must be rejected. If cleanup cannot finish, return SERVFAIL rather than applying a newer generation concurrently.

## Capacity and operational constraints

Admission must reserve enough unique /32 slots for all addresses in a DNS reply before adding any. Align agent `max_routes`, ROS peer input limit, ACK payload/size limit, guard cap and barrier capacity. Exhaustion rejects new answers and alerts; it must not delete a live route. Keep configurable headroom, monitor active/guards/barriers/pending operations, remaining slots, oldest draining prefix, last confirmed ACK, disk errors, ROS scheduler duration, route write rate and CPU. `arrival rate of new unique IPs × retention + existing hot prefixes + fault/drain reserve` is only a sizing estimate. With 512 slots and 24h minimum retention, 21 new unique IPs/hour already consumes ~504 slots under a uniform-rate simplification; indefinite long-lived connections and pinned barriers make the actual bound worse. Avoid excessive static route/firewall writes and flash wear.

## Required implementation and integration tests

- Model/unit: all state transitions, all-or-nothing multi-IP admission, TTL/send deadline, pin vs concurrent retire, stale generation and duplicate/reordered ACK, capacity pressure, disk-sync error, restart at each intent/effect/ACK boundary, clock forward/back, shared-IP references, conntrack wait, BGP add/delete failures and no-op idempotence. The supplied model exercises a strict subset only.
- Real ROS isolated source only: verify actual static blackhole persistence, firewall rule insertion and matching before accepts and FastTrack, NAT original/reply tuple detection, no hardware/bridge/IPv6 bypass, in-flight packet/conntrack quiescence bounds, same-IP concurrent new connections, withdrawal/re-add and stale snapshot, capacity failure, controlled power loss before/after configuration readback and after each controller phase. Confirm old cached and long-running connections, test negative cases and restoration; packet capture and actual egress are required. Do not run crash/reboot tests against the household production path without a tested rollback.

Neither the model nor a future successful controlled-client test can guarantee behavior of clients outside the assumptions. If unconditional no-leak is required, the final per-prefix barrier cannot safely be removed just because compliant DNS TTL and observed conntrack have expired; retaining such barriers indefinitely does not provide bounded state. Consider a fixed fail-closed routed range with an explicit proxy architecture instead.
